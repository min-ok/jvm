# Верификатор программ

`Verifier` — статическая проверка готовой `Program` перед исполнением. Он не запускает код, а просматривает массив инструкций и таблицу констант, строит граф потока управления и собирает **все** найденные проблемы, а не останавливается на первой. Проблемы бывают двух уровней: ошибки и предупреждения.

- `verifier.h` — `Verifier`, `VerifyError`, `Severity`, а также `Format`, `DCheck`, `ControlFlow`, `OpInfo` (описание инструкции).
- `verifier.cpp` — таблица инструкций `op_table`, построение графа и сами проверки.

## Место в конвейере

Загрузчик (`load_program`) проверяет текст: синтаксис, число аргументов, диапазоны регистров и непосредственных значений. Он не знает программы целиком, поэтому не может проверить то, что зависит от неё как от целого: попадает ли переход внутрь кода, существует ли константа с таким индексом, может ли исполнение выйти за конец программы, достижим ли конец. Это делает верификатор.

```cpp
Program program = load_program(path);

Verifier verifier(program);
std::vector<VerifyError> problems = verifier.verify();

bool has_errors = false;
for (const VerifyError &e : problems) {
    bool is_error = e.severity == Severity::Error;
    std::cerr << (is_error ? "error" : "warning")
              << " at pc " << e.pc << ": " << e.message << "\n";
    has_errors = has_errors || is_error;
}
if (has_errors) {
    // программу не запускаем
}
```

Пустой результат означает, что проблем не найдено. Результат, состоящий только из предупреждений, не означает, что программу нельзя запускать.

## API

```cpp
explicit Verifier(const Program &program);
std::vector<VerifyError> verify();
```

- Верификатор хранит **ссылку** на `Program`, поэтому программа должна жить дольше верификатора.
- `verify()` можно вызывать повторно: перед каждым запуском список проблем очищается.
- Возвращается копия списка.

```cpp
enum class Severity { Error, Warning };

struct VerifyError {
    size_t pc;           // индекс инструкции в program.code; для проблем всей программы — 0
    Severity severity;
    std::string message;
};
```

## Порядок работы

1. Список проблем очищается.
2. Для каждой инструкции по порядку (`pc = 0 … code.size()-1`) вызывается `check_instruction`.
3. После этого вызывается `check_program`: проверки всей программы и анализ графа.
4. Возвращается накопленный список.

Из-за такого порядка проблемы уровня программы идут **после** проблем отдельных инструкций, независимо от своего `pc`.

## Описание инструкций: `OpInfo`

Каждой инструкции в `op_table` (`unordered_map<Opcode, OpInfo>`) соответствует запись:

```cpp
struct OpInfo {
    Format format;     // Abc или Ad
    bool use_a;        // поле a используется
    bool use_b;        // поле b используется (только для Abc)
    bool use_c;        // поле c используется (только для Abc)
    DCheck d;          // как проверять поле d (только для Ad)
    ControlFlow flow;  // как инструкция передаёт управление
};
```

Форматы кодирования:

| `Format` | Поля | Примеры |
|---|---|---|
| `Abc` | три регистра `a`, `b`, `c` | `ADD`, `MV`, `PR`, `STP` |
| `Ad` | регистр `a` и число `d` | `LI`, `LK`, `JMP`, `JZ` |

Режимы проверки `d`:

| `DCheck` | Смысл `d` |
|---|---|
| `None` | число или смещение, проверять нечего |
| `Constant` | индекс константы |
| `Jump` | адрес перехода |

Виды передачи управления и следующие инструкции:

| `ControlFlow` | Инструкции | Следующие инструкции |
|---|---|---|
| `Normal` | арифметика, `MV`, `LI`, `LF`, `LK`, `IN`, `PR` и т. д. | `pc + 1` |
| `Stop` | `STP` | нет |
| `Jump` | `JMP` | `d` |
| `Conditional` | `JZ`, `JNZ` | `d` и `pc + 1` |
| `Call` | `CALL` | `d` и `pc + 1` |
| `Return` | `RET` | нет |

Инструкции с видами `Normal`, `Conditional` и `Call` могут «провалиться» на следующую (`pc + 1`); для них проверяется выход за конец программы.

### Содержимое таблицы

| Инструкции | Формат | Используются | Проверка `d` | `flow` |
|---|---|---|---|---|
| `STP` | Abc | — | — | `Stop` |
| `MV` | Abc | a, b | — | `Normal` |
| `LI`, `LF` | Ad | a | `None` | `Normal` |
| `LK` | Ad | a | `Constant` | `Normal` |
| `JMP` | Ad | — | `Jump` | `Jump` |
| `JZ`, `JNZ` | Ad | a | `Jump` | `Conditional` |
| `ADD`, `SUB`, `MUL`, `DIV`, `MOD` | Abc | a, b, c | — | `Normal` |
| `NEG` | Abc | a, b | — | `Normal` |
| `FADD`, `FSUB`, `FMUL`, `FDIV` | Abc | a, b, c | — | `Normal` |
| `FNEG` | Abc | a, b | — | `Normal` |
| `I2F`, `F2I` | Abc | a, b | — | `Normal` |
| `EQ`, `LT`, `LE`, `FEQ`, `FLT`, `FLE` | Abc | a, b, c | — | `Normal` |
| `IN`, `FIN`, `PR` | Abc | a | — | `Normal` |
| `CALL` | Ad | a | `Jump` | `Call` |
| `RET` | Abc | a | — | `Return` |

Опкод, которого нет в таблице, считается неизвестным (см. ниже).

Чтобы описать новую инструкцию, достаточно добавить строку в `op_table` с нужным `OpInfo`.

## Проверки отдельной инструкции

Для каждой инструкции:

1. **Опкод известен.** Если записи в `op_table` нет — ошибка `unknown opcode`, остальные проверки для этой инструкции пропускаются.
2. **Неиспользуемые поля равны нулю** (`check_unused_fields`):
   - если `use_a == false`, то `a` должно быть 0;
   - для формата `Ad` на этом проверка полей заканчивается (`b` и `c` входят в `d`);
   - для формата `Abc` дополнительно: при `use_b == false` поле `b` равно 0, при `use_c == false` поле `c` равно 0.
3. **Поле `d`** (`check_d_field`):
   - `Constant`: `d` должно быть меньше `program.constants.size()`, иначе `there is no constant with that number`;
   - `Jump`: `d` должно быть меньше `program.code.size()`, иначе `jump target out of range`.
4. **Номера регистров** (`check_registers`): используемые регистры должны быть в диапазоне `0..28` (`MAX_REGISTER`). Проверяется `a` (если `use_a`), для формата `Abc` ещё `b` и `c` (если используются). Иначе ошибка вида `register 'a' must be in range [0; 28]`.

Проблемы одной инструкции накапливаются: например, у `JMP` с ненулевым `a` и целью за пределами кода будут обе.

## Проверки программы целиком

`check_program` выполняется после проверки инструкций:

1. **Программа не пуста.** Пустой `code` — ошибка `program is empty` (`pc = 0`), дальнейшие проверки пропускаются.
2. **Анализ графа потока управления** (`check_program_graph`, описан ниже).

## Граф потока управления

### Построение

`build_graph` строит для каждой инструкции список следующих (функция `next_instructions` по виду `flow`, см. таблицу выше). Инструкции с неизвестным опкодом рёбер не имеют. Рёбра, ведущие за пределы кода (`next >= code.size()`), в граф не попадают: недопустимые цели переходов уже сообщены проверкой `d`, а «провал» за конец ловится отдельной проверкой.

### Достижимость и выход за конец

Обход графа (поиск в глубину со стеком) от инструкции 0:

- для каждой достижимой инструкции, чей `flow` — `Normal`, `Conditional` или `Call`, и которая стоит последней (`pc + 1 >= code.size()`), — ошибка `execution can go past the end`;
- инструкция с неизвестным опкодом не раскрывается: её следующие инструкции из неё не достигаются;
- каждая **недостижимая** инструкция даёт предупреждение `instruction is unreachable`.

### Есть ли путь к завершению

Строится обратный граф (рёбра развёрнуты), затем:

1. В исходное множество «может завершиться» попадают достижимые инструкции `STP`. Только `Stop` считается завершением программы; `RET` не считается.
2. От них по обратным рёбрам распространяется признак: всё, из чего можно дойти до `STP`, помечается.
3. Если инструкция 0 не помечена — ошибка `program has no path to termination` (`pc = 0`).

Это единственная проверка, которая ловит бесконечные циклы: она срабатывает, когда из точки входа вообще нельзя дойти до `STP`. Цикл на одной из веток при наличии другого пути к `STP` не обнаруживается.

## Таблица проблем

| Сообщение | Уровень | `pc` | Причина |
|---|---|---|---|
| `unknown opcode` | Error | инструкции | опкода нет в `op_table` |
| `field 'a' must be 0` | Error | инструкции | у инструкции не используется `a`, но оно ненулевое |
| `field 'b' must be 0` | Error | инструкции | формат `Abc`, `b` не используется, но ненулевое |
| `field 'c' must be 0` | Error | инструкции | формат `Abc`, `c` не используется, но ненулевое |
| `there is no constant with that number` | Error | инструкции | индекс константы `d` вне `program.constants` |
| `jump target out of range` | Error | инструкции | адрес перехода `d` вне `program.code` |
| `register 'a' must be in range [0; 28]` | Error | инструкции | номер регистра `a` вне диапазона |
| `register 'b' must be in range [0; 28]` | Error | инструкции | номер регистра `b` вне диапазона |
| `register 'c' must be in range [0; 28]` | Error | инструкции | номер регистра `c` вне диапазона |
| `program is empty` | Error | 0 | в программе нет инструкций |
| `execution can go past the end` | Error | последней инструкции | достижимая последняя инструкция может передать управление дальше конца кода |
| `program has no path to termination` | Error | 0 | из точки входа нельзя дойти ни до одного `STP` |
| `instruction is unreachable` | Warning | инструкции | в инструкцию невозможно попасть от точки входа |

Порядок проблем в результате: сначала проблемы отдельных инструкций (по возрастанию `pc`), затем `execution can go past the end` (в порядке обхода графа), затем предупреждения `instruction is unreachable` (по возрастанию `pc`), затем `program has no path to termination`.

## Что верификатор не проверяет

- Типы значений в регистрах (целое или вещественное), чтение регистров до записи.
- Состояние памяти и кучи, глубину стека вызовов, парность `CALL` и `RET`.
- Допустимость `RET` вне функции: для графа `RET` просто инструкция без следующих.
- Значения непосредственных операндов у инструкций с `DCheck::None` (например, у `LI` и `LF`).

## Особенности реализации

- Конструктор `Verifier` определён прямо в заголовке.
- Граф строится как приближение: `CALL` имеет рёбра и в тело функции (`d`), и на следующую инструкцию (`pc + 1`), то есть возврат из функции считается всегда успешным.
- Предупреждение о недостижимости выдаётся для каждой инструкции отдельно, а не для блока кода целиком.
- Если инструкция 0 имеет неизвестный опкод, то помимо `unknown opcode` будет выдана и `program has no path to termination`: из неё не строятся рёбра.
